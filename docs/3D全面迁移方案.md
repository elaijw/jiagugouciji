# 甲骨奇谭 · 全面转向 3D 的技术方案与风险评估

> 撰写依据：当前仓库实际代码（`js/` 约 17,100 行、`assets/` 22 MB、5 个 GLB 模型），
> 以及已跑通的阶段①原型（`#/world`，3D 王邑聚落）。
> 本文对应开发指令里的「先提交五项分析，再实现第一个可运行原型」——
> 原型已完成并通过验收，本文同时作为阶段②~⑤的施工图。

## ① 迁移到完整 3D 的技术方案

### 1.1 现存的工程约束（不能破的三条）

| 约束 | 现状 | 为什么不能动 |
|---|---|---|
| 零构建 | 全站传统 `<script>` 顺序加载，无打包器 | 双击 `index.html` 也要能跑；部署是静态托管 |
| 零 ESM | 全局 `App` 命名空间 | Three.js r149 用 UMD 版（`vendor/three.min.js`），改用 ESM 会让 `file://` 直开失效 |
| 零 CDN | 所有资源本地 | 内网 / 离线可演示 |

结论：**不引入 React、不引入 three 的 examples 模块（OrbitControls / GLTFLoader / BufferGeometryUtils 等），
不引入物理引擎。** 需要的功能自己写，这是这套项目一贯的做法，也保证了迁移期间原站始终可用。

### 1.2 渲染层的四个文件分工

```
js/world/world-build.js   场景构建（地形/道路/建筑/碑林/碰撞盒/交互点）—— 无渲染循环
js/world/world3d.js       运行时（渲染器/相机/输入/碰撞解算/拾取/步态）
js/world/world.js         HUD 与面板（靠近提示、字碑面板、地点碑、城门、探方）
css/world.css             3D 场景的全屏接管样式与移动端控件
```

这样切的理由：`world-build` 是纯函数式的"造世界"，可以在 Node 里或后续的离线工具里复用；
`world3d` 只管一帧一帧地跑；`world` 只管 DOM。三者没有循环依赖，后续接讨伐/任务时不用改动前两个。

### 1.3 关键实现决策（都已落地）

- **几何合并 `mergeGeos()`**：几何转非索引 → 按 attribute 拷进大 `Float32Array` → 一材质一 mesh。
  整座聚落 95 个 mesh、约 12 个 draw call。这是没有 `BufferGeometryUtils` 时的替代方案。
- **单一高度场 `terrainH(x,z)`**：低频 sin/cos + value noise + 外圈山脊（`rim²×15`）。
  角色贴地、建筑落座、道路贴合、草丛分布全部读同一个函数，所以永远不会互相穿帮。
- **道路用三角带 `ribbon()`**：逐顶点采样地形，而不是铺薄箱子（薄箱子贴坡会出现锯齿台阶）。
- **庑殿顶 `hipRoofGeo(w,d,h,inset)`**：矩形檐口四角 + 屋脊，前后坡 + 左右山面 + 底面封板，按尺寸缓存。
  先试过 `ConeGeometry` 旋转 45°，俯视像菱形帐篷，已废弃。
- **碰撞**：圆 vs 轴对齐盒，分轴判定（撞墙可顺着滑），`{x,z,hx,hz,h}` 带高度。
- **相机避让**：`rayBoxT()`（slab 法射线-AABB）+ `camTerrainClear()`（沿视线 12 步采样地形）。
  没有这两步，角色一贴墙相机就钻进建筑/土里，画面糊成一片土色 —— 这是原型期踩过的坑。
- **拾取**：`Raycaster` 只对 `userData.kind === 'char'` 的碑面求交；未命中时退到屏幕空间，
  取 46 px 内最近的一块碑（手指比 0.5×0.8 米的碑面粗得多）。
- **路由**：`#/world` 与 `#/museum` 并列，各自 create / dispose；离开时 canvas 归零（验收项 `allCanvas: 1`）。

## ④ 需要制作的模型清单（Blender → GLB）

现状：角色与建筑都是**程序化几何拼装**（龟宝约 40 个 primitive，整座聚落 95 个 mesh）。
这在阶段①够用，但讨伐与近景互动必须换成真模型。

| 优先级 | 模型 | 用途 | 规格建议 |
|---|---|---|---|
| **P0** | 龟宝（骨骼版） | 玩家 | ≤ 6k 三角面；骨骼：根/髋/脊/头/四肢/尾，共 ≤ 24 骨；动画：待机、走、跑、受击、施法 |
| **P0** | BOSS ×1（建议先做「禽兽」区的鹿/牛形） | 首个 3D 讨伐 | ≤ 12k 面；待机/攻击/受击/倒地 四段 |
| **P1** | BOSS 其余 4 个（天象/山川/草木/人居） | 五区各一 | 同上 |
| **P1** | 宗庙、观星台、屋舍、畜圈、陶窑 | 聚落地标 | 低模 + 贴图，单件 ≤ 2k 面 |
| **P1** | 可交互文物：甲骨片、青铜鼎、陶罐、龟甲、刻辞骨臼 | 3D 考古互动 | 每件 ≤ 800 面，可点击高亮 |
| **P2** | 植被/岩石变体、火塘、旗帜、路标 | 场景填充 | 保留程序化，只补 2~3 个变体 |
| **P2** | 展台、玻璃罩、牌坊 | 展馆已有 | 直接用现有 GLB |

命名与目录约定：`assets/models/<类别>/<名字>.glb`，单位米，Y 轴向上，原点在脚底中心，
材质导出为 PBR（metallic-roughness），贴图 ≤ 1024，单模型 ≤ 300 KB。

## ⑤ 开发风险与优先顺序

### 5.1 风险（按严重度）

1. **GLB 骨骼动画缺失（最高）**
   `glb.js` 只解析网格与材质，不处理 skinning / animation。
   → 要么自己补 skinning（约 300 行矩阵蒙皮 + 关键帧插值），要么改用"刚体部件 + 程序化摆动"（当前做法）。
   *缓解*：阶段③的 BOSS 先用分层刚体拼装 + 程序化动作，把骨骼留到阶段⑤；龟宝继续程序化步态。

2. **移动端性能**
   当前 38 张碑面纹理各 128×200（约 4 MB 显存），95 个 mesh。
   → 合图集（一张 1024² 放 38 字）可把 38 次纹理切换降到 1 次；低端机自动关阴影、DPR 限 1.5。

3. **无物理引擎 → 战斗手感全靠自写状态机**
   受击顿帧、位移、无敌帧、技能判定全部手写，容易"打赢了也不爽"。
   *缓解*：先做 1 个 BOSS 把手感打磨到能接受，再复制到五个。

4. **自动化测试在 swiftshader 下不稳**
   首帧编译着色器会卡住 1~2 秒，按键测试会误判"走不动"（本轮已遇到，已用"等帧数 > 8"规避）。
   → 所有交互测试必须带帧数预热。

5. **线上版本与缓存**
   线上是 `?sharecode=` 链接，`index.html` 资源版本号必须逐次递增，否则改了看不到。
   → 每次发布前统一升版本号；**未经确认不覆盖线上**（本轮改动尚未发布）。

### 5.2 优先顺序（建议的下一步）

```
②-a  分区子场景：从聚落走进「天象/山川/草木/禽兽/人居」任意一片，
     独立的 3D 空间（复用 world-build 的地形与材质函数），内含碑林 + 探方 + 一件文物
②-b  文物交互：靠近 → 拾取 → 3D 展示（旋转查看）→ 认字写入存档
③    3D 讨伐原型：1 个 BOSS，识字正确率直接决定技能强度与 BOSS 血量
④    串联：奖励落进场景、解锁下一区、回馆动线
⑤    模型 / 动画 / 音效 / 移动端 / 性能
```

推荐先做 **②-a**：它复用现有全部代码，能最快把"聚落 → 分区 → 互动"这条主链打通，
也是后面讨伐（③）的前置场景。
